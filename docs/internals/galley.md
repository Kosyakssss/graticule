# Galley: the editing core

`crates/galley` holds what an editor needs below the screen. It depends on Ledger and nothing of the kernel's, so any program can edit text with it.

## Storage and history

A `Doc` keeps its text in a rope (ropey, MIT), so inserting into a hundred-megabyte file costs what inserting into a line does. It is a Ledger field like `Text`: every replacement records an `Op::Splice` while a transaction is open, and undo, redo, saving and replays work on those operations without knowing about ropes. Splices name places in bytes, as `Text`'s do, because that is what Ledger's operations already carry; `Doc` turns them back into characters when it applies one and refuses one that doesn't land on character boundaries or doesn't find the text it expects to remove, so a stale operation fails rather than corrupting the text. Saving writes the whole text as one string, which is fine for the sizes the demo apps keep in their facts; a file-backed document would save the file instead.

## Positions and selections

Everything the app sees counts characters, not bytes, so a position never falls inside a character. Motions step over grapheme clusters, what a reader sees as one character (an accented letter written as two code points, an emoji with a skin tone), by running `unicode-segmentation`'s grapheme cursor over the rope's chunks; words are runs of one class (letters and digits, punctuation, space), the way Helix and Vim see them.

`Selections` holds at least one span, kept in order, with overlapping or identical spans merged after every change, and one of them primary. Spans that only touch stay apart, so two adjacent selected words remain two.

The `Doc` owns its selections, because every edit has to carry them and undo has to bring them back. When a transaction ends, the `Doc` compares its selections with a snapshot taken at the start and records an `Op::Select` if they moved, after the splices. Ledger's history keeps a change that only moves a selection as a move, never as a step of its own, even inside a document: undo puts the moves back together with the step they came before, so the cursor returns to where the user was when they made the change. Applying an `Op::Splice` doesn't touch the selections; the `Op::Select` recorded with it does, so undo and redo restore them exactly instead of mapping them again.

## Changes made at once

`Changes` is every replacement of one edit, as ranges of the text before it, sorted and never overlapping. The `Doc` applies them from the last to the first so earlier ranges still mean what they meant, and each selection is mapped through them: a position after a change shifts by what it added or removed, one inside a replaced range moves to the end of the replacement, and one at the very place of an insertion moves after it, so a cursor stays after what was typed at it. Typing, deleting, a new line (indented like the line it breaks) and replacing every match are all a `Changes`, so each is one undo step at every cursor.

## Find

`find_all` walks the rope's bytes once with a Knuth–Morris–Pratt table: time grows with the text, never with the text times the pattern, and nothing is copied out of the rope. On a long text it belongs in a job, like every scan.

Replacing every match is split for that reason. `Doc::replacement` runs in a job on a clone, which shares the rope's storage, so sending it costs nothing: it finds the matches, builds the text from the first match to the last as one string, the new rope and the cursors mapped through the changes. `Doc::take` on the main thread then only swaps the rope in and records one splice whose strings were built in the job, so undo is one step. A replacement carries the document's revision, a count of changes since it was loaded, and is refused if that moved, since its places would no longer mean what they meant. The command log keeps only the range, the new text and the cursors; a replay has no prepared rope and makes the splice itself. Mapping cursors through changes is one sweep over both, since both are in order: with a hundred thousand cursors, mapping each through every change was ten billion steps.

Finding is split the same way between the screen and the text. `ui.editor_with_find` underlines matches only on the lines it builds, searching each line's own text, so it costs what the screen costs; a match that runs across a line break is not underlined. An input method composes into the focused editor as into a field: the window keeps the unfinished text, the editor's lines get it through their look, and only the line holding the primary cursor draws it, pushing the rest of that row along; the candidate window is placed at the primary cursor's row and cell. Stepping to the next or previous match (`Doc::find_from`, then `Doc::go_to`) looks through the whole text, so it is a job.

Adding the next match is split the same way, since the next place may be anywhere: `Doc::next_match` finds it in a job on a clone and `Doc::take_next` adds it as a selection, refused if the revision moved; the log keeps only where it was. Adding a cursor on the line above or below is a motion from the primary cursor and costs nothing. Cursors live with the text but not in its saved value, so the commands that only add cursors say how many there are now; that is also how Assay sees that they did something.

## The editor

The kernel can't depend on Galley, since Galley must build without a screen, and Galley can't depend on the kernel. They meet in Ledger. `ledger::Typed` is what a person did in an editor: typed text, a new line, a delete, a move by a `Travel`, a click at a position, select all, collapse. It travels as `Change::Typed` inside an ordinary `Edit`, so the app routes it with `edit.apply(self)` like a field's edit, the command log records it, and replays repeat it. `ledger::Editable` is what the kernel reads from the text to draw it: how many lines, one line's text in chunks, where a line starts, which line a position is on, the cursors, and the selected text for copying. `Doc` implements both; another text type could too.

`ui.editor` reads only the lines that show, from the scroll position the window keeps for it, and writes each as an `EditLine` node with its selection ranges in the tree's marks and its cursors in the tree's carets. Each line wraps by the same rule as a text area (`ledger::wrap`), so it is an `EditLine` as many rows tall as it wraps into. The rule lives in Ledger rather than the kernel because Galley needs no screen and still has to move by it: Up and Down in the editor arrive as `Travel::RowUp(width)` and `RowDown(width)`, carrying the width the editor last wrapped at, and Galley wraps only the cursor's line and its neighbour to find the row above or below at the same column in cells. The width travels in the log too, so a replay moves the same way whatever the window's size. The view needs the width before layout has run, so it takes the one layout gave last time, kept by the window as a ruler's is, and a change of width builds the view again. After typing or a move the view itself brings the primary cursor's line into sight: it walks back from that line only as far as one screen of wrapped rows holds, so the cost stays with what is on screen however long the text. Copy and clicks need the facts at a time when the view isn't running, so the tree keeps two erased functions per editor (`EditorInfo`): one asks for the selected text, the other where a line starts, so a click turns into a character position without the kernel knowing the text's type.

The keys follow each platform's conventions in `field::editor_key`, beside a text field's, so the two never disagree. Typing joins into one undo step per word by the same rule as a field's.

## Folding

Folds are kept by the `Doc` beside its selections, not by the view, because they have to move with the text the same way: each fold is the characters from the start of its first hidden line to the end of its last, mapped through every change as a cursor is, and dropped when a change reaches into it, its line breaks included, since then its lines are no longer the ones that were folded. Typing at the end of the line a fold hangs under leaves it closed. A cursor that ends up inside a fold, by a click, a find or select all, opens it, so nothing the user is working on is ever hidden. Up and Down step over a fold, as from the line it hangs under to the line after it.

Folds travel with the selections in the same `Op::Select`, as a `folds` entry beside the spans, which is left out when there are none, so a log written before folding reads the same. That makes folding behave as moving the cursor does: never an undo step of its own, and undo of the next change brings back the folds as they were before it.

Which lines to fold is the app's. `Doc::fold` takes any lines, which is where a syntax tree's blocks would come in; `Doc::block` finds, on a copy in a job, the lines indented further than the cursor's, or else the block the cursor's line belongs to, since a block may run to the end of a long file. The kernel reads folds through `Editable::folded` and `Editable::shown`, which default to none, so the editor skips folded lines and the wheel scrolls by the lines that show.

## Marks: syntax and spelling

What a parser or a spellchecker says of a text is `ledger::Marks`, re-exported by Galley: ranges of characters, each a keyword, a type name, a literal, a comment or a mistake. It lives in Ledger beside `Editable` because the kernel draws it and Galley must not need the kernel. Mistakes are kept apart from the rest, since a misspelt word in a comment is both; within each kind ranges are in order and apart, so the editor finds a line's marks by two binary searches and reads only the lines it shows.

Marks are worked out over the whole text, so they belong in a derived value: the app names a function from its `Doc` (and anything else, such as the file's name) to `Marks`, the kernel runs it off the main thread after each change, and the view hands the latest to `.marked(…)` on the editor. Until a newer value arrives the editor draws the last one, whose places may be a few characters off for a frame; they are clamped to each line, so nothing breaks. This is where tree-sitter plugs in: its incremental parse is the derived function's business, and its folds go through `Doc::fold`. Galley ships no parser; the face's marker of Rust is a few dozen lines to show the hook working.

`Spelling` is the hook a spellchecker fills: whether it knows a word and what might have been meant. `Doc::check_spelling` walks a range of the text word by word and marks those it doesn't know; a word is letters with apostrophes inside, and a run holding a digit or an underscore is a name and left alone, so code checks sensibly. Which spellcheckers ship is open question 15.

## Laws

`crates/galley/src/laws.rs`: any sequence of edits at any cursors, over text with combining marks, emoji and line breaks, undoes to the start and redoes to the end through its recorded operations, bringing back the selections each time as well as the text; and the selections are valid after every step. The edits include folding any lines, folding the block at the cursor and unfolding, and validity includes the folds: in order, apart, each whole lines under a line that shows, with no cursor inside one; undo and redo bring the folds back with the selections. Every app with an editor also gets the universal laws, which Assay drives by typing into its editors as well as its fields.
